# Lessons learned

Real problems met while building this lab. Each one changed a script, a check or a process.

| # | What happened | Root cause | Fix | Lesson |
|---|---|---|---|---|
| 1 | In the gate test, lint and unit tests failed — but never read the code | `requests==2.19.1` needs `idna<2.8`; `pip install` failed first | Lint installs only pinned `ruff`; rerun showed `S602` caught on its own | A red pipeline is only useful if it is red for the right reason |
| 2 | A deleted branch's fake token broke the `main` pipeline | gitleaks scans `git log --all`; the runner's cached clone kept deleted refs | `GIT_STRATEGY: clone` + `--log-opts=$CI_COMMIT_SHA` | Deleting a branch does not delete a secret: rotate, then rewrite history |
| 3 | Kyverno: `DENIED: access forbidden` | Deploy-token creation failed; an empty credential was written to the secret | Use GitLab's own service; refuse empty values before writing | Read errors layer by layer (DNS ok → TLS ok → auth failed); guard against empty secrets |
| 4 | Trivy supply-chain attack, March 2026 (CVE-2026-33634) | Malicious releases under legitimate tags | All CI tools pinned by digest; cool-down period | Security tools are part of the supply chain too |
| 5 | Kaniko archived by Google | Upstream maintenance ended | Maintained fork, pinned | Tool choices need ongoing maintenance review |
| 6 | Smoke test `wget --ca-certificate` failed | Alpine's wget is BusyBox | `curl --cacert` plus a negative test (no CA → must fail) | A negative test proves verification really happens |
| 7 | Ansible `--check` failed on `dpkg_selections` | Package not installed in check mode | `when: not ansible_check_mode` | Dry runs must be clean or nobody uses them |
| 8 | ZAP raised 3 warnings | Missing security headers | Middleware + unit test + `--no-server-header` | Fix, lock with a test, re-scan: 3 → 0 |
| 9 | Falco did not alert on a shell | `kubectl exec -t` without `-i` allocates no TTY | Test with `-it` | No alert is not always a tool failure — check the rule's conditions |
| 10 | API key from Vault was 49 characters, not 48 | `openssl rand` adds a newline; `vault kv put key=-` stored it | `tr -d '\n'`; verify expected length after delivery | Invisible characters in secrets cause "correct but does not work" bugs |
| 11 | A long terminal log was pasted into the bastion shell | Clipboard held a saved log instead of a command | Unwanted commit reverted with `git revert` (no force-push); terminal with paste protection; outputs exported to files | Prefer scripts with `set -euo pipefail` over long pasted blocks |
| 12 | A GitHub token was pasted into a chat | Human error while copying | Revoked and regenerated immediately; format-checked hidden input | Rotate first, investigate second |
| 13 | A step script stopped silently | `set -o pipefail` treated an expected "not found yet" as fatal | Handle expected failures explicitly (`\|\| LEN=0`), fail loudly with details | Fail-fast needs explicit handling of expected errors |
| 14 | Claude Code (Bun) would not start on ss-mgmt | ss-mgmt was built by hand before Terraform and kept Proxmox's default CPU type `kvm64`, which has no SSE4.2; found by comparing with ss-gitlab | `qm set 104 --cpu host` on pve1 | A bootstrap machine outside IaC must be documented as a deliberate exception, or its drift goes unnoticed |
| 15 | Claude Code test: which commands a `Read(*.tfstate)` deny rule actually blocks | Deny rules match the path in Claude's file tools and in shell readers it recognises (`cat`, `head`, `jq` were blocked); `python3 -c "open(...)"` read the same dummy file, and the rules do not apply outside the project directory at all | Tested with a dummy file only; the real exposure is the Terraform state itself: not in Git, but plain text on ss-mgmt's disk (now a **Gap** in `security-controls.md`) | Deny rules are a guardrail, not a sandbox: protect the data at rest, not just the tool |
| 16 | `tfstate-migrate.sh` stopped with "lineage farkli" after moving state to GitLab, although all 9 instances and IDs were there and `terraform plan` showed no changes | Migrating into an empty remote backend: `PersistState` refreshes, finds no remote snapshot and generates a new lineage (`uuid.GenerateUUID`); terraform v1.16.6, `internal/states/remote/state.go` | Verification now compares resource addresses + IDs with the encrypted backup and requires `plan -detailed-exitcode` = 0; lineage is printed for information only | Verify the property that matters (same resources, no drift), not metadata the tool may legitimately change; read the source before changing the check |
| 17 | Terraform talked to the Proxmox API without TLS verification (`PROXMOX_VE_INSECURE=true`) | Proxmox uses its own CA; `bpg/proxmox` has no CA option (v0.118.0: `RootCAs` unset, Go system pool); the endpoint was an IP that is not in the certificate's SAN (cert made with an older IP); pveproxy does not send the root CA in the chain | CA fingerprint checked over a separate channel; `scripts/tf.sh` passes system bundle + pve CA as `SSL_CERT_FILE` to Terraform only; endpoint moved to a SAN name; wrong-CA test must fail | Same as the `GIT_SSL_CAINFO` mistake in `ai-assisted-engineering.md`: an env var that replaces the trust store needs the system roots too; scope trust to one process, then prove it with a negative test |
| 18 | `scripts/tf.sh` (wrapper for Terraform) silently bypassed the Claude Code rules `ask: terraform apply` and `deny: terraform destroy` | Permission rules match the command text; `scripts/tf.sh apply` does not start with `terraform apply` | Added `ask: Bash(*tf.sh apply*)` and `deny: Bash(*tf.sh destroy*)` | When a tool is wrapped in a script, its deny/ask rules must move to the script too; review permission rules whenever a wrapper is added |
| 19 | `scripts/ci-status.sh` was allow-listed in Claude Code (runs without a prompt), but the assistant could edit it; an allow rule for the bare name `ci-status` would also have run any `ci-status` earlier on `PATH` | Permission rules match command text, not the file's content or owner; deny rules on Edit/Write do not stop `python3` or a shell writing the file (#15); `~/.local/bin` is first on `PATH` and user-writable | Approved copy at `/usr/local/bin/ci-status`, `root:root 0755`, installed by the human with `sudo install`; allow rule on the absolute path only; `Edit/Write(scripts/ci-status.sh)` denied as a guardrail; rule 7 in `CLAUDE.md` | A script on the allow list must be immutable for the AI: the deny rule is a guardrail, the real control is file ownership (root:root 0755) |
| 20 | Moving a Secret from env to a volume broke the admin endpoint (503) | Secret volume files are `root:root` with `defaultMode`; without `fsGroup` the non-root app cannot read `0440` | `fsGroup: 10001`; caught by ZAP (new WARN 100000) | Verify end-to-end after a deploy change; a green unit test cannot see cluster file permissions |
| 21 | IaC gate looked green while it scanned only part of the code | Checkov 3.3.26 (Terraform): `--skip-path` builds an invalid regex (`module_finder.py`: `'\|'.join(f"({excluded_paths})")` joins the characters of a list's string form); with several `-d` flags every report counted the same 9 Proxmox resources (passed 18 → 36 → 54 → 72) and the secure samples were never parsed; and Checkov has no rules for `bpg/proxmox`, so the real on-prem code had 0 checks | `scripts/iac-scan.sh` scans one directory per run; `scan-gate.py` fails a report with zero checks; custom Proxmox rules give the on-prem module 18 checks; negative copy fails all of them | Check *what* a scanner scanned (resource count, per directory), not just its exit code; a gate that scans nothing must be red |
| 22 | The GCP default service account was not detected in the insecure sample | `CKV_GCP_30/31` match only the literal `<n>-compute@developer.gserviceaccount.com`; a reference through `data.google_compute_default_service_account` is invisible to it. A YAML graph policy did not see the raw reference either | Python check `CKV_SS_3` on the raw resource config; insecure sample fails, secure passes | Test detections with the realistic form of the misconfiguration, not the textbook one |
| 23 | The assistant tried to delete merged remote branches without asking (the push failed); later a requested deny rule `Bash(git push * :*)` did not block `git push origin :branch` | Deleting a ref is irreversible but looks like routine cleanup; in Claude Code a trailing `:*` is the legacy prefix syntax, so the rule did not mean what it said | Deny rules for `--delete`, `-d`, `:refspec` (as `Bash(git push * :**)`) and `git branch -D` in both repositories, each tested with a harmless dry-run | Text rules can be bypassed (aliases, `git -C`, other spellings) and can silently be wrong; the real control is server-side: GitLab protected branches (no deletion of `main` by push) and role permissions of the credential the bastion pushes with |
| 24 | The plan gave the DefectDojo CI user the role `API_Importer` on each product; on 3.3.300 `/api/v2/roles/` and `/product_members/` returned 404 | DefectDojo 3.x moved per-product RBAC to the commercial Pro plugin (`dojo/authorization/authorization.py`): OSS checks only superuser, staff, and a product's `authorized_users`. The roles table still exists in the database, which made the plan look plausible | CI user `gitlab-ci` is in `authorized_users` of both products, never staff (asserted by Ansible and by the token script): view/add/edit/import, no delete. The Ansible bootstrap fails if `authorized_users` disappears from the API | Read the authorization code of the exact version you deploy; role names in the database or in old docs are not a permission model |
| 25 | The DefectDojo initializer would have written a generated admin password into the container log | `complete_initialization.py` generates `DD_ADMIN_PASSWORD` (and the Jira webhook secret) when unset and prints it (`Admin password: …`); `docker logs` keeps it | Both generated up front with `openssl rand` into ansible-vault; the admin password is passed only to the one-shot initializer through a 0600 env file. Verified: 0 matching lines in the initializer log | Before the first start of any service, read what its bootstrap prints; a default that logs a secret is still a leak |
| 26 | The new nginx on ss-sec failed to reload, and Ubuntu's default would have allowed TLS 1.0/1.1 | Ubuntu's `nginx.conf` sets `ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3` and `ssl_prefer_server_ciphers` at http level; repeating them in `conf.d` is an error | The protocol line in `nginx.conf` is managed (TLS 1.2/1.3), the handler runs `nginx -t` before reload, unknown SNI is rejected at the handshake. Tested from the server side with `openssl s_client -tls1/-tls1_1` (both refused) | Test the server, not the client: `curl --tlsv1.1` failed only because the local OpenSSL refuses TLS 1.1 |
| 27 | A negative TLS test (`curl --cacert <public CA>`) passed although it should have failed | Ubuntu's curl keeps the system CA directory (`capath`) when `--cacert` is given, and ss-mgmt trusts the lab CA system-wide | Negative tests use `--cacert <file> --capath <empty dir>`; only then did the public-CA test fail with `unable to get local issuer certificate` | A negative test must fail for the reason you intend; check what else the tool trusts |
| 28 | Every `main` pipeline closed all ~170 image findings in DefectDojo and opened them again (`created=164 closed=170`) | DefectDojo's Trivy parser uses the scan `Target` as `file_path`, which is part of the dedup hash; the target contains the image digest, which changes with every build | `defectdojo-upload.py` removes `@sha256:…` from `ArtifactName` and `Target` before the import; the commit stays in `version`/`commit_hash` | A green upload is not a working register: check the reimport counters (`created/closed/untouched`). Churn silently resets every SLA clock |
| 29 | The first SonarQube analysis passed the Quality Gate with an empty condition list | SonarQube computes no new-code measures on a project's first analysis; with "number of days" the baseline is the newest analysis older than 30 days, and while none exists, the first one. A gate defined only on new code therefore evaluates nothing on day one | Checked the measures, not the green status: the overall values (0 bugs, 0 vulnerabilities, 0 hotspots, 100 % coverage) cover the existing code; the second analysis evaluated the conditions (negative test: `new_vulnerabilities=3` → red; clean code → `new_bugs=0`, `new_vulnerabilities=0` → green). `sonarqube-local-scan.sh` prints every condition with its actual value | Same as #21: a gate is only evidence if you can see what it evaluated. "Passed" with zero conditions means "not measured" |
| 30 | The SonarQube gate "0 new bugs, 0 new vulnerabilities" did not match the server's default model | SonarQube 10.8+ starts in MQR mode (software-quality impacts instead of bug/vulnerability types); the mode can only be changed through API v2 (`/api/v2/clean-code-policy/mode`), API v1 refuses it "for security reasons". Also, a new quality gate in 26.9 already carries the default Clean-as-You-Code conditions | `sonar-admin.py` sets Standard Experience mode via v2 before any analysis and reconciles the gate to exactly the four required conditions (extra defaults removed) | Read the server's current model before encoding a policy in it; check what a "create" call creates |
| 31 | The read-only kubeconfig for the assistant existed and passed 13/13 `can-i` checks, yet the assistant's plain `kubectl` was still `system:admin` (`system:masters`, `can-i '*' '*' -A` → yes) | `Read(~/.kube/**)` is a Claude Code file rule; kubectl opens `~/.kube/config` itself. The plan to force the read-only file with `env.KUBECONFIG` plus text deny rules (`--kubeconfig`, `KUBECONFIG=`) would still have left the admin file readable by the same Unix user (any script, `bash -c`, Python) | The human asked for proof before removing the `-o yaml/json` deny rules; `kubectl auth whoami` without `KUBECONFIG` showed `system:admin`, so the rules stayed. `scripts/kubeconfig-lockdown.sh` (run by the human with sudo) moves the admin kubeconfig to `/etc/securestream/admin.kubeconfig` (`root:root 0600`), links `~/.kube/config` to the read-only file and proves `whoami` = `claude-readonly`, `can-i get secrets` = no; the `k3s` role now writes the admin file there | The boundary moves from text matching to RBAC only when the privileged credential is out of the assistant's file-system reach. Test the identity the tool actually uses (`auth whoami`), not the credential you meant it to use. NOPASSWD sudo remains the next layer (security-controls §1) |
| 32 | The `kubectl -o yaml/json` deny rules had been the only thing standing between the assistant and Secret values | Text rules match the command, not the identity: any other spelling (`-o=jsonpath`, `get --raw`, a script) would have passed them, and the admin kubeconfig gave full access (#31) | The boundary moved from text matching to RBAC and file ownership: read-only ServiceAccount, admin kubeconfig `root:root 0600` outside the user's home, `~/.kube/config` → read-only file. Only after plain `kubectl auth whoami` showed `claude-readonly` and `can-i get secrets -A` → no did the human remove the `-o yaml/json` rules; text rules stay as guardrails (`get secret*`, `--kubeconfig`, `KUBECONFIG=`) | A control the assistant can talk its way around is a guardrail; the boundary is what the server or the kernel enforces. Remove a guardrail only after the boundary behind it is proven with the identity actually in use. Remaining layer: same Unix user with sudo (security-controls §4) |
| 33 | `--diff` can leak secret file contents: the assistant was about to run `k3s.yml --check --diff` and send the output to the screen; the role writes the admin kubeconfig (client key) and two templates with the k3s join token | `--diff` prints before/after of every file a task writes. Here the four tasks happened to carry `no_log: true`, which also hides the diff, but nothing stated that intent, and an earlier `appsec.yml --check --diff` log in the session scratchpad held full diffs of other files (0 secrets, 6 censored tasks, 1 false-positive pattern: source code of `sonar-admin.py`) | The human stopped the run. Every secret-bearing task in the `k3s` role now has `diff: false` next to `no_log: true`; the check ran with the log in `/dev/shm` (0600), only task names, status and PLAY RECAP shown, secret patterns counted (all 0), log shredded; scratchpad logs deleted. The same run found a check-mode artefact: `Kurulu k3s sürümü` was skipped in check mode, so the download looked "changed" (now `check_mode: false`): all three nodes `changed=0` | A dry run is still output: treat `--diff` like `cat` on every file the play writes. Mark secret tasks with `no_log` and `diff: false`, filter what reaches the screen, and keep logs out of persistent paths |
